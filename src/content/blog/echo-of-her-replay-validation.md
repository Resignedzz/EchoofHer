> 这轮实践最重要的进展，不是把某个分数调高，而是建立了一条更可靠的工作方式：保留原始请求，区分真实缺陷与判分争议，用最小改动修复，再通过独立批次真实重放验证。

今天没有继续增加新能力，而是集中处理一个更基础的问题：当她已经会选择和使用技能之后，怎样确认最终结果真的变好了，而不是只在代码层面看起来修好了。

围绕此前积累的 50 条真实 check 样本，今天完成了从人工归因、最小修复到真实重放的完整闭环，并把重放过程沉淀成了可复用技能。

## 一、起点：50 条真实样本中的 5 条低分

初始质量基线为：

- 50 条真实 check；
- 45 条 pass、5 条 low、0 条 unavailable；
- 总体平均分 0.91，低分率 10%。

逐条对照用户请求、技能产出、最终回复和 judge 判词后，5 条低分并不是同一种问题：

| 样本 | 技能 | 原分数 | 失败层级 |
|---|---|---:|---|
| #1 整理三条笔记 | writer | 0.3 | 判分尺度：已完成简单整理，却被按长文标准扣分 |
| #2 单词统计 | coder | 0.4 | 最终回复：技能产出了代码，回复只剩思路 |
| #3 Python 排序方法 | researcher | 0.4 | 检索：没有拿到可定位的官方页面 |
| #4 生成器表达式 | researcher | 0.4 | 检索：技术内容完整，仍缺官方来源 |
| #5 MDN 缓存指令 | researcher | 0.6 | 最终回复：资料里已有引用，回复全部删除 |

这意味着不能统一用“模型能力不足”解释，更不能直接根据低分自动生成学习经验。

## 二、先修真实工程缺陷：让必要交付物不再丢失

最终回复层新增了确定性补救机制：

- coder 用户明确要求代码，而回复缺代码块时，从技能结果补回完整代码；
- researcher 用户明确要求来源、链接或引用，而回复不可定位时，从技能结果补回真实引用或链接；
- 补救内容同步进入流式输出、数据库消息和 check 输入，避免用户看到的回复与判分输入不一致。

researcher 则增加了一次官方来源定向补查。用户明确要求官方来源且首轮没有命中时，会针对 `docs.python.org`、`developer.mozilla.org`、`who.int` 等域名补查；仍未找到时必须诚实说明，不能用二手资料冒充官方来源。

第一轮修复后，真实重放证明方向有效，但也暴露了新的问题：无关引用可能被误标成可定位来源，官方内容可能没有 URL，任务回复还可能被 512 tokens 截断。

随后又做了最小残留修复：只从结构化结果中补真实官方域名来源，在参考资料中保留 URL，并将路由命中的任务回复输出预算放宽到 1024 tokens，普通闲聊仍保持 512 tokens。

## 三、判分本身也要校准

修复交付物之前，先要确认“低分”到底是不是真实失败。第一轮复核发现 judge 存在系统性偏差：

- 一个 WHO 建议时长样本没有给出核心数值，只因诚实说明资料失效、没有虚构而得到 pass/0.9；
- 同样是官方来源缺失，有的样本被判 0.4，有的仍是 0.9；
- #4 的回复已经给出两个官方章节名称，判词却写成“完全回避官方来源”；
- #1 已经把三条笔记串成完整脉络，只因没有扩写成长文被判 0.3。

这些问题指向同一个原因：judge 对“是否忠于参考资料”的权重过高，对“用户任务是否完成”的权重不足。

因此只重写了判分提示词，把优先级明确为：

1. 任务完成度；
2. 是否忠于参考资料、是否虚构；
3. 来源是否可追溯；
4. 诚实说明资料不足，不能替代未完成的核心任务；
5. 用户未要求扩写时，不因回复简短判低分。

输出协议、0.6 及格线和 server 侧硬校验都没有改动。判分尺度后来还做了第二次校准，专门处理“交付完成但附带追问”的情况，见第五节。

## 四、把重放验证沉淀成技能

为了避免每次临时写脚本、手工等待 check，今天新增了工作区技能 `echo-low-score-replay`。

它支持：

- 按 `review_queue` 样本 ID 选择重放范围；
- 为每轮实验生成独立 sid 和批次；
- 等待 SSE 与异步 check 落库；
- 汇总实际技能、最终回复、check 状态和低分原因；
- 通过 dry-run 只检查样本，不发送真实请求。

技能同时明确了边界：不修改历史 `review_queue`，不重判历史 check，不自动生成 tip，也不把一次重放当作最终真值。

使用技能复放原 5 条样本（批次 `replay-20261120-skill-a-01..05`）后的结果：

| 样本 | 原分数 | 复放结果 | 关键观察 |
|---|---:|---:|---|
| #1 writer 整理笔记 | 0.3 | 0.55 low | 素材截断，用评价代替交付，结尾还有追问 |
| #2 coder 单词统计 | 0.4 | pass | 最终回复直接包含完整代码块 |
| #3 Python 排序官方来源 | 0.4 | pass | 给出两个可定位的 `docs.python.org` 链接 |
| #4 生成器表达式官方来源 | 0.4 | 0.45 low | 技术对比完整，仍未召回 Python 官方页面 |
| #5 MDN 缓存指令 | 0.6 | 0.4 low | 出现参考资料中不存在的 MDN URL，引用编号也错位 |

这轮重放同时暴露了三个新问题：

- 补救层过度触发，把无关的 `[1][2][3]` 标成“可定位来源”；
- researcher 即使命中官方内容，也可能没有可用的 URL；
- 任务型回复被 512 tokens 截断，来源说明写到一半就结束。

对应的最小修复是：只从结构化结果中补真实官方域名来源；参考资料和输出都保留官方 URL；任务型回复的输出预算放宽到 1024 tokens，普通闲聊仍为 512。

更值得注意的是 #5：它不只是“没搜到 MDN”，最终回复还给出了参考材料中不存在的 MDN 地址，引用编号也与资料对不上。也就是说，格式上有 URL，不等于来源真实可追溯。

## 五、writer 的问题不是一个点，而是三层叠加

writer 样本暴露了三类不同原因。

### 1. 技能素材被截断

medium 文章要求 800–1200 字，却仍使用默认 512 tokens，导致参考素材曾在“人的记忆”这样的半句处结束。最终回复随后把第三条笔记判断为“原文没写完”。

现在按文章长度设置生成预算：short 768、medium 1536、long 3072 tokens。

### 2. 最终回复没有稳定交付清单

即使素材完整，模型有时仍会说“你整理得挺清楚”，把任务理解成评价用户成果，而不是直接整理。

现在对明确的多条目整理请求增加了按用户原文补清单的兜底，并在 writer 注入规则中禁止错误开场和交付后的用途追问。补救判断还修复了一个正则问题：`**加粗段落**` 不应被当作 `*` bullet。

### 3. 开场和结尾发生了角色错位

除了清单交付不稳定，最终回复还出现过一种更细微的问题：助手没有站在“帮我整理的人”这个位置，而是站到了“评价我整理得怎么样的人”这个位置。

**修复前的开场：**

> 嗯，你整理得挺清楚的呀，这三条笔记其实挺有逻辑的……

用户给出的是三条原始笔记，并要求助手整理。这句话却把用户说成已经完成整理的人，既误解了任务角色，也推迟了正式交付。

**修复前的结尾：**

> 你是打算拿去做笔记或者分享给别人吗？

这条追问发生在三条内容已经给出之后，因此不是“缺少必要澄清”，而是额外延伸话题。它不会抹掉已经完成的交付，但会让一个简单整理任务显得不够直接，也曾被 judge 过度放大为任务未完成。

本次在 writer 的最终回复注入规则中增加了两条明确约束：

- 整理/总结任务直接交付结果，不说“你已经整理好了”，也不评价用户的整理成果；
- 结果给出后不追问用途，不询问是否继续。

这里的修复对象是让模型在生成时就避免这些表达，而不是等流式回复结束后再把开头或结尾删掉。它只针对明确的 writer 整理/总结任务，不改变普通闲聊中的自然回应方式。

**修复后的实际表现：**

- 开场变为“三条笔记整理如下：”，或直接说明“我帮你把这三条整理成一份小笔记”；
- 结尾用一句话总结或行动建议收束，例如“想开始的话，挑一条先做两周就好”，不再附带问题；
- 三次复放都没有出现角色误判式夸奖，也没有出现结尾追问。

### 4. judge 把轻微表达问题判成核心任务失败

有一条 low 样本已经完整列出早睡、运动、记录三条内容，却仍因结尾附带追问、没有复刻参考文章风格而得 0.55。

这类结果不应和“没有交付”混为一谈。judge 规则因此进一步校准：

- 用反问或询问是否需要来替代交付，仍判未完成；
- 核心交付完整后附带的多余追问，只记轻微问题，不能单独判失败；
- 用户未要求扩写、成文或特定风格时，不因简短、口语化或未复刻参考文风而判失败。

最终批次 `replay-20261120-writer-judge-a-01..03` 连续复放三次，均直接交付三条整理结果，无错误开场、无结尾追问，check 全部 pass。

## 六、今天得到的几个经验

**交付物缺失和判分争议必须分开。** 丢代码、丢引用是工程缺陷；已经交付却因简短被判低分，是 judge 校准问题。

**有 URL 不等于来源可信。** MDN 样本曾出现参考材料中不存在的 URL 和错位引用编号。来源检查必须验证它是否来自真实检索结果，而不只是检查格式。

**确定性补救也需要回归测试。** 补救层曾误把无关 `[n]` 标成可定位来源，也曾把加粗段落误判成列表。规则越确定，越要测试它的误触发边界。

**不能只看 pass 数量。** writer 中间批次多次为 2/3 pass，但低分样本实际已经完成核心交付。只有重新阅读用户请求和最终回复，才能避免把判分噪声当成新的功能缺陷。

## 七、当前状态与下一步

这一轮的改动集中在四处：

| 位置 | 改动 |
|---|---|
| 判分提示词 | 两轮校准：任务完成优先级、来源追溯边界、附带追问不算未完成 |
| 最终回复层 | 新增确定性补救：缺代码补代码，缺可定位来源补真实来源 |
| researcher | 官方来源识别、一次定向补查、命中后保留 URL、未命中禁止编造 |
| writer | 按文章长度设置输出预算，禁止错误开场与交付后追问 |

验证状态：

- `python -m pytest tests -q`：**55 passed**；
- 静态检查：0 个问题；
- 未修改 0.6 阈值、历史 `review_queue` 状态和已落库的 check；
- 未生成或注入 tip；
- 复放使用的临时后端已停止，避免后续误测旧进程。

writer 专项问题已完成修复和三次真实复放验证，但整个质量工作尚未全部完成：

- #4 仍需解决 Python 官方页面召回失败；
- #5 还需处理参考材料外虚构 MDN URL、引用错位的问题；
- M2 仍需用干预重放器和对照组完成因果验收；
- 在门禁满足前，不进入自动 tip 生成和规模扩写。

今天最重要的进展，不是把某个分数调高，而是建立了一条更可靠的工作方式：**保留原始请求，区分真实缺陷与判分争议，用最小改动修复，再通过独立批次真实重放验证。**
